# Detection Engineering: Tracking Empire PsExec Lateral Movement in Splunk

## 📌 Project Overview
This project demonstrates how to ingest, analyze, and detect advanced adversary lateral movement techniques using **Splunk Enterprise**. 

The core of this case study is a **PsExec lateral movement attack** executed via the **Empire post-exploitation framework**, simulated using log data from the https://github.com/OTRF/Security-Datasets.

### The Security Challenge
Unlike standard automated malware, this attack showcases an adversary attempting to blend into normal network traffic by renaming malicious services to mimic legitimate Windows updates. By analyzing Windows Event Logs and Sysmon data, this project demonstrates my ability to write Splunk Processing Language (SPL) to bypass superficial indicators (like file names) and detect malicious behavior directly in the operating system.

### 2. Detecting Remote Service Creation (PsExec Behavior)
Before deep-diving into a full investigation, my first task is to determine whether this alert is a **False Positive** (authorized administrative work) or a **True Positive** (unauthorized malicious activity). 

Since PsExec is a dual use tool heavily utilized by both IT administrators and threat actors, I need to inspect the specific telemetry around the service creation to find anomalies. 

The security alert came in as `Persistence: New Windows Service Created`. By mapping this alert to the **MITRE ATT&CK Framework**, I immediately identified that Windows monitors new service installations under **EventID 7045**. I executed the following query to filter for this activity and bypass any file-renaming tricks:

```spl
index=security_datasets EventID=7045
| table _time, host, ServiceName, ImagePath, AccountName
```

### 💡 Real-World Scenario Next Steps: Parent-Child Process Tracking
While this specific simulation dataset focuses heavily on the service installation layer, **in a real-world production environment**, an analyst would immediately pivot to tracking the process genealogy. 

To uncover the exact commands the attacker executed after the service was established, the next logical step in an interactive threat hunt would be to query Sysmon data (**EventCode 1**) to map out the parent-child relationship:

```spl
# Real-World Scenario Follow-up Query
index=security_datasets EventCode=1 ParentImage="*powershell.exe" OR ParentImage="*psexesvc.exe"
| table _time, host, Image, CommandLine, User
```

By leveraging this query in a standard live environment, we can isolate whether the malicious service spawned interactive command utilities (`cmd.exe`), allowing us to map out the adversary's actions post-exploitation.

## 🧠 Threat Intelligence & Analyst Mindset

### Understanding "Living off the Land" (LotL)
PsExec is a legitimate administrative tool created by Microsoft. Attackers abuse these trusted tools because they are already permitted by local firewalls and often bypass basic antivirus software. As an analyst, detecting LotL techniques requires looking for behavioral anomalies rather than relying solely on file signatures.

### The Attack Mechanics (What we are hunting for)
When PsExec is executed remotely against a target machine, it triggers a predictable sequence of events in Windows:
1. **Network Connection:** The attacker authenticates via SMB.
2. **Service Creation:** A temporary Windows service is installed to run the payload with `SYSTEM` privileges.
3. **Execution:** The service launches a process (like `cmd.exe` or `powershell.exe`) giving the attacker an interactive shell.

By knowing this behavior, we can target specific Windows Event IDs (like **Event ID 7045: New Service Installed**) to find the exact moment the compromise happened, regardless of whether the attacker renamed the binary file or the service itself.

## 🔮 Modern Threat Context: Why a 2020 Case Study Remains Vital in the AI Era

A common question in modern security monitoring is whether analyzing a legacy attack framework (like Empire PsExec from 2020) is still relevant when modern threat actors heavily utilize AI to automate attacks. The short answer is **yes**. While the speed and automation of attacks have evolved through AI, the underlying operating system mechanics and post compromise objectives remain virtually identical.

### 1. LotL is Still the Dominant Evasion Strategy
Threat actors do not rely solely on custom AI malware; instead, they abuse built in administrative tools to blend in with legitimate network traffic.
- **The Evidence:** According to the **Trellix CyberThreat Report**, legitimate system utilities like `cmd.exe` and `PowerShell` remain the top tools utilized by Advanced Persistent Threats (APTs) to maintain stealth.
- **The Trend:** The **ENISA Threat Landscape Report** highlights a continuous surge in Living off the Land (LOTL) techniques, specifically noting how cybercriminals mask their Command and Control (C2) communication through trusted infrastructure.
- **Stealth Operations:** Global research from the **Fortinet Global Threat Landscape Report** confirms that cybercriminals increasingly use these trusted administrative protocols to move laterally and escalate privileges undetected.

### 2. The Core Telemetry Has Not Changed (Windows Fundamentals)
Whether a lateral movement attack is executed by a human hacker or an automated, AI driven playbook, the destination operating system must still process the actions according to Windows architectural rules.
- **The Artifact:** For an adversary to execute remote commands via PsExec, the system *must* install a temporary service. As documented in defensive research by **JPCERT/CC**, this action triggers a highly predictable trail of telemetry: specifically **Windows System Event ID 7045 (New Service Installed)**.
- **The Analytical Takeaway:** Modern AI-powered SIEM tools require human baseline tuning. An analyst who does not understand fundamental core artifacts like Event ID 7045 cannot effectively write detection rules, validate automated AI alerts, or hunt for hidden anomalies.

## 🛑 Mitigation & Recommendations
To protect an enterprise network from this type of "Living off the Land" lateral movement based on my findings, the following controls should be implemented:

1. **Restrict Local Administrator Accounts:** Prevent local administrator accounts from connecting over the network via SMB (use Group Policy to deny network logon rights for local admins).
2. **Monitor Administrative Shares:** Monitor or restrict access to default administrative shares (`C$`, `ADMIN$`), as these are mandatory requirements for PsExec to pivot.
3. **Deploy & Configure Sysmon:** Deploy Sysmon with a tailored configuration file (e.g., SwiftOnSecurity) to specifically log and alert on anomalous service executions and parent-child process relationships.
